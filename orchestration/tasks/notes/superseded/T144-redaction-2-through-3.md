# T144 — ACP: непустой селектор модели в левой панели

**Статус:** active. Исполнитель — любой агент; задание самодостаточно,
предыдущий контекст и переписка не нужны.
**Переписан 2026-07-28 архитектором.** Предыдущая редакция писалась до бампа на
2.0.0 и устарела целиком: в ней предлагалось вендорить патч крейта, чтобы
добавить полю `models` дорогу до клиента. **Поля `models` в протоколе больше
нет.** Всё, что ниже, сверено с исходниками в кэше cargo, а не с docs.rs.

**Зоны файлов:** `crates/services/src/hermes_acp/{client.rs,session.rs}`,
`crates/app/src/side_panel_left/composer.rs` (рендер списка).

**Отчёт захода 2:** `orchestration/tasks/report/T144-acp-session-models-report-2.md`
(отчёт захода 1 отклонён и лежит в `rejected/`).

## Симптом

Дропдаун Model в левой панели пуст, `composer_selected_model` пустой.
В логе на каждую сессию — `No session.models and no config_options` (33 раза
за сутки).

## Что установлено — сверено с исходниками, НЕ перепроверять

Версии: `agent-client-protocol 2.0.0`, `agent-client-protocol-schema 1.5.0`,
`hermes-agent 0.18.2`.

**1. Концепция `models` из протокола удалена.** В схеме 1.5.0
(`src/v1/agent.rs:1087-1112`) `NewSessionResponse` несёт ровно четыре поля:

```rust
pub struct NewSessionResponse {
    pub session_id: SessionId,
    pub modes: Option<SessionModeState>,
    pub config_options: Option<Vec<SessionConfigOption>>,   // ← замена
    pub meta: Option<Meta>,
}
```

`SessionModelState`, `availableModels`, `SetSessionModelRequest` — **ноль
вхождений** во всём крейте и во всей схеме. Замена — обобщённые опции сессии:
`SessionConfigOption { id, name, description, category, kind }`
(`v1/agent.rs:2513`), где `category: Some(SessionConfigOptionCategory::Model)`
(`v1/agent.rs:2485`), а `kind` для выбора модели — `SessionConfigSelect`
(`v1/agent.rs:2430`) со списком `SessionConfigSelectOption` и группами.
Смена значения — `SetSessionConfigOptionRequest` (`v1/agent.rs:2707`).

Вывод: **вендорить патч (вариант B старого брифа) больше незачем** —
патчить нечего, поля нет. Вариант A (`on_session_start`) тоже мёртв: он
отдаёт `ActiveSession`, а не сырой ответ (`session.rs:220-224`).

**2. Агент говорит на старом диалекте.** На проводе за сутки:

```
"models":{"availableModels":[…]}   16 раз
"configOptions"                     0 раз
```

Hermes 0.18.2 шлёт снятую конструкцию и не шлёт новую. Даже идеальный клиент
увидит пусто.

**3. Библиотека теряет и новое поле — ровно как раньше теряла `models`.**
`ActiveSession` (`2.0.0/src/session.rs:506-529`) хранит `session_id`,
`update_rx`, `update_tx`, `modes`, `meta`, `connection` — `config_options`
в структуре **нет** (`grep -c config_options session.rs` → `0`).
А `response()` (`session.rs:570-574`) пересобирает ответ заново:

```rust
NewSessionResponse::new(self.session_id.clone())
    .modes(self.modes.clone())
    .meta(self.meta.clone())
```

То есть `config_options` всегда `None` у любого клиента, который работает
через `ActiveSession`. Наш `client.rs:146` читает это поле правильно — просто
там гарантированно пусто.

**Это тот же баг библиотеки, что и год назад, только с новым именем поля.**

## Что сделать

Три фронта. Порядок важен: без первого остальные непроверяемы.

### 1. Апстрим-issue — СДЕЛАНО архитектором, работы не требует

`ActiveSession` не сохраняет `config_options` из `NewSessionResponse`, и
`response()` их не отдаёт. Любой клиент на `ActiveSession` не может показать
ни селектор модели, ни любую другую опцию сессии.

Issue открыт: **https://github.com/agentclientprotocol/rust-sdk/issues/301**.
Пока он не закрыт, обходной путь (пункт 2) остаётся в силе.

### 2. Обходной путь на нашей стороне — но сначала докажи, что он нужен

Если апстрим не даёт быстрого пути, взять данные там, где они есть.
Единственный честный вариант из старого брифа, который выжил, — вариант C:
`AcpAgent::with_debug` уже видит весь стдио-трафик (`transport.rs:85-129`),
включая сырой ответ на `session/new`.

Это грязь — разбирать протокол в обход библиотеки, которая его уже разобрала.
**Поэтому обязательное условие: изолировать.** Одна функция, один комментарий
с номером апстрим-issue и словом «удалить, когда починят», ноль JSON-разбора
за её пределами. Если пишешь это — в отчёте объясни, почему не дождались.

### 3. Клиентская часть — она понадобится в любом случае

Панель должна уметь показывать список моделей и менять значение.

> **Поправка после захода 2 (2026-07-28).** Здесь раньше стояло «менять
> значение через `SetSessionConfigOptionRequest`». Это верно для протокола
> 2.0.0, но **неверно для нашего агента**: Hermes 0.18.2 `configOptions` не
> понимает, у него смена модели живёт на старом методе `session/set_model`
> (`server.py:1995`). Пока агент говорит на старом диалекте — слать надо
> старый метод; подробности и способ в разделе «ЗАХОД 3». Когда агент
> переедет на `configOptions`, этот код меняется вместе с перехватом.

### 4. Что НЕ делать в этой задаче

Не чинить агента. Hermes шлёт старый диалект — это задача в его репозитории
(там уже лежит один наш патч, см. скилл `hermes-acp-tool-completed`).
Зафиксируй факт в отчёте и остановись.

## Ч1. Убрать глобальный статик — обязательно

`INTERCEPTED_MODELS: StdMutex<Option<SessionModels>>` — процесс-глобальный,
не привязан ни к сессии, ни к агенту. Это не педантизм, а три живых сценария:

1. **Несколько агентов.** У нас реестр `agents.toml` (T138). Переключишь
   агента — увидишь модели предыдущего.
2. **Список зависит от провайдера и меняется между сессиями.** Замерено по
   логу за сутки: список приезжал 17 раз — **дважды по 287 моделей** (Nous
   Portal, до 11:10) и **пятнадцать раз по 36** (openrouter, с 13:59, после
   правки `model.provider` в конфиге агента).
3. **Глобал переживает сессию.** Сработай перехват утром — весь день
   показывались бы 287 моделей, которых у агента уже нет.

**Что сделать:** хранить перехваченные модели рядом с сессией — там же, где
живут `session_id` и `modes` (`SharedSession` / `ActiveSession`-обёртка в
`client.rs`), ключом по идентификатору сессии. Сбрасывать при `session/new`.
Если `session_id` в момент перехвата ещё неизвестен (строка `session/new`
разбирается до того, как сессия оформлена) — взять `id` JSON-RPC запроса из
той же строки и связать по нему; в ответе он есть.

Требование про изоляцию остаётся в силе: одна функция, ноль JSON-разбора за
её пределами, пометка DELETE с номером апстрим-issue.

## Ч2. Номер issue вместо заглушки

Подставить `#301` вместо `#XX` в пометках DELETE (`client.rs:134`, `:182`,
`:195` и рядом), чтобы через полгода было понятно, чего ждём и когда этот код

## D6 — выбор модели уходит не тем методом

Замер приёмки (см. `report-log/T144-…-report-2.md`, раздел D6):
`client.set_model("nous:anthropic/claude-opus-4")` вернул `Ok(())`, на проводе
оказался **`session/set_mode`**, а следующий ход агент отработал на прежней
`tencent/hy3:free`. Успех ложный.

Причина в `client.rs:752`: `set_model_on_active` строит
`SetSessionModeRequest::new(session_id, model_id)` — то есть кладёт
идентификатор модели в поле `mode_id`. Агент такой запрос принимает молча:
его `set_session_mode` (`~/.hermes/hermes-agent/acp_adapter/server.py:2029`)
написан так, чтобы «ACP-клиенты не падали на смене режима», и сохраняет что
угодно.

Смена модели у агента реализована отдельно —
`set_session_model` (`server.py:1995`), метод `session/set_model`, параметры
`{ sessionId, modelId }`, ответ `SetSessionModelResponse` (пустой объект).
Именно его надо звать.

## Сложность: типа запроса в крейте больше нет

`SetSessionModelRequest` удалён из `agent-client-protocol 2.0.0` вместе со
всей концепцией `models` (см. раздел «Что установлено» выше). Поэтому взять
готовый тип неоткуда — его надо объявить у себя.

Крейт это прямо поддерживает: `JsonRpcRequest` — производный трейт с
макросом (`agent-client-protocol-2.0.0/src/jsonrpc.rs:4160-4175`, там же
пример в докстринге):

```rust
#[derive(Debug, Clone, Serialize, Deserialize, JsonRpcRequest)]
#[request(method = "_hello", response = HelloResponse)]
struct HelloRequest { name: String }

#[derive(Debug, Clone, Serialize, Deserialize, JsonRpcResponse)]
struct HelloResponse { greeting: String }
```

Объявленный так тип уходит в тот же `conn.send_request_to(Agent, request)`,
которым уже пользуется `set_model_on_active` — переписывать транспорт не
нужно, меняется только тип запроса.

## Что сделать

1. Объявить локальный тип запроса на метод `session/set_model` с полями
   `sessionId` / `modelId` (camelCase на проводе — сверь с сырой строкой в
   логе, а не с догадкой) и пустым типом ответа.
2. Переключить `set_model_on_active` на него. Поле `mode_id` больше не
   трогать: смена **режима** — отдельная функция и отдельный метод, их
   путать нельзя.
3. Изоляция и срок жизни, как у остального обхода: одна пометка DELETE с
   `#301` и объяснением, что тип объявлен локально, потому что протокол
   2.0.0 выкинул `models`, а агент 0.18.2 ещё говорит на старом диалекте.
   Когда сойдутся — этот код уходит вместе с перехватом.
