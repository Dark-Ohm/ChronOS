# T216 — Отчёт: Right panel resize — абсолютная самокорректирующаяся модель

**Дата:** 2026-08-03
**Статус:** Закоммичено `0b3aed7` (вместе с T218 — per-tab resize память), юнит-тесты
green, release-билд OK. Живой прогон НЕ отмечен в таске (файл ещё в `active/`) — см.
«Верификация».

## Что было не так

T210 (покадровые дельты) и T214 (anchor + `start_x += Δw` в `render`) — обе модели
**накапливающие**: ширина считалась от запомненного состояния, а не от текущей геометрии.

Панель прибита к правому краю (`Anchor::TOP | Anchor::RIGHT`), поэтому рост ширины
двигает **левую** кромку окна влево. Координаты `DragMoveEvent` — оконно-локальные,
т.е. меряются от этой самой уезжающей кромки. `window.resize()` на Wayland асинхронна:
между записью в state и реальным `configure` от компоновщика прилетают события,
померенные по **старой** геометрии. Накапливающая модель обязана держать свою
бухгалтерию в такт с ack'ами — она не может, и каждое рассинхронизированное событие
засчитывает смещение дважды.

**Замер (старый бинарь, живой drag влево):** ширина шла
`895 → 806 → 792 → 773 → 684 → 524 → 382 → … → 40 … → 960` — разгон в оба упора.

Ложный след для протокола (из таска): первый диагноз «drag-события не доходят» был
неверен — отсутствие строк `resize drag started/move` объяснялось тем, что эти строки
добавлялись той же правкой, а бинарь был старый; доказательством обратного служили
десятки `window.resize` из `update_resize` в тех же логах.

## Решение (закоммичено `0b3aed7`)

**Абсолютная самокорректирующаяся модель** — `resize_target_width` в
`crates/app/src/side_panel_right/mod.rs:148`:

```
pointer_screen = window_left + current_x,  window_left = screen_right - actual_w
держим схваченную точку под курсором  =>  desired_left = pointer_screen - grab
desired_w = screen_right - desired_left  =  actual_w - current_x + grab
```

`actual_w` берётся из `window.bounds()` — из той поверхности, относительно которой
померен `current_x`, а **не** из нашего state (он убегает вперёд между ack'ами).
Накопления нет: отставший кадр повторяет ту же цель вместо того, чтобы её удваивать.
Побочно это ровно то поведение, которое просил пользователь — **кромка приклеена к
мыши**, а не догоняет её.

Из `view.rs` (render) убрана компенсация `resize_start_x += Δw` — при абсолютной
модели она считала бы то же смещение кромки второй раз.

**Раскрытие rail → content остаётся на mouse-down** (важно). Попытка убрать
авто-раскрытие сломала drag полностью: rail-only окно шириной 40px, первое движение
уводит курсор за пределы поверхности раньше, чем GPUI успевает начать drag-сессию
(`resize drag started` есть, `resize drag move` — ноль). Раскрытие даёт жесту достаточно
широкое окно. При раскрытии grab-offset переписывается в новый кадр:
`grab = press_x + (target - w)`, иначе первое же событие прочитает курсор как «глубоко
в body» и схлопнет панель назад.

В том же коммите — T218: per-tab resize память (`tab/mod.rs`, `tabs.rs`) — ширина
восстанавливается при возврате на вкладку, повторный клик по активной вкладке не
сбрасывает её (`same_tab_reclick_preserves_resize`, `switch_tab_restores_per_tab_resize_memory`).

## Тесты

Юнит-покрытие зовёт настоящий код (`resize_target_width`), не переписывает формулу в
тесте (урок T164):

- `drag_left_grows_right_anchored_width` — 20px влево → +20px ширины;
- `drag_target_is_idempotent_across_a_stale_frame` — **регрессионный guard**: тот же
  ввод по отставшей геометрии даёт ту же цель (не разгон), а после ack'а ширина
  держится;
- `grab_offset_survives_the_rail_to_content_expand` — нет схлопывания после раскрытия,
  drag дальше влево даёт +100px;
- `drag_target_clamps_to_both_bounds` — упоры `RAIL_ONLY_WIDTH` / `MAX_WIDTH`;
- плюс существующие `resize_clamps`, `peek_close_suppressed_while_resizing`,
  `exclusive_px_dock_vs_rail`, `rail_only_default_width`.
