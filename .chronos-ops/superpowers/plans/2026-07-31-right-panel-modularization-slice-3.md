## 2. Границы слайса

**В слайсе:**

1. Контракт вкладки: у каждой вкладки — свой модуль и своё состояние,
   создаваемое лениво при первой активации.
2. `System` переезжает в этот контракт первой и служит образцом.
3. Набор растёт до **четырнадцати** по §4.1: добавляются `Preview`,
   `Inspector`, `Build`, `SourceControl`.
4. Пустые вкладки получают **честное** пустое состояние по §13 вместо
   `"coming soon"`: что это за инструмент, почему пусто, что появится.

**Вне слайса — осознанно:**

- Реальное содержимое Files / Terminal / Build / Preview. Это **слайс 4**
  по §14 («Developer hybrid-workbench minimum»). Слайс 3 строит место, куда
  их класть, и не строит их самих.
- Gamer-инструменты — слайс 5.
- Переезд `gpui-component` с воркетри-пути (см. §5, техдолг).

## 3. Архитектурное решение — контракт вкладки

**Принято: ленивый реестр `AnyView` на вкладку.**

Каждая вкладка — обычная GPUI-сущность со своим `Render`. Панель держит
`HashMap<PanelTab, AnyView>` и создаёт вьюху при первой активации вкладки,
не раньше. Активная вкладка рендерится как один дочерний элемент.

```rust
// side_panel_right/view.rs — точка входа контента вместо when()-ветвей
let content = self.tab_view(self.active_tab, window, cx);
```

**Почему так, а не иначе:**

- **Не `Box<dyn Trait>` с ручным рендером.** Вкладке нужно собственное
  состояние между кадрами (позиция скролла, раскрытые узлы дерева, PTY).
  В GPUI это `Entity<T>`, а не голый объект; попытка обойти сущности
  кончится ручным протаскиванием контекста через каждый вызов.
- **Лениво, а не всё сразу.** Терминал не должен поднимать PTY, пока
  пользователь не открыл вкладку. Это же снимает вопрос стоимости при
  четырнадцати вкладках: не открыл — не заплатил.
- **Кэш, а не пересоздание.** Ушёл со вкладки и вернулся — состояние на
  месте. Пересоздавать вьюху на каждом переключении значит терять позицию
  скролла и перезапускать PTY; это баг, а не оптимизация.
- **Сброс кэша — только при смене режима**, и то не обязательно. Решение:
  **не сбрасывать**. Вкладка, ушедшая из набора режима, просто не
  показывается; вернулась — состояние на месте. Если это окажется дорого
  по памяти, это видно замером, а не догадкой.

**Чего контракт НЕ делает:** не трогает `tabs.rs::for_mode` /
`resolve_for_mode` / `PanelTab::ALL` — композиция по режиму принята в T165 и
живёт отдельно от того, чем вкладка наполнена.

## 4. Честное пустое состояние (§13)

`"{label} — coming soon"` заменяется на общий компонент пустого состояния:
иконка вкладки, название инструмента, одна строка «что это будет», и
**никаких обещаний сроков**. §13 спеки: «missing integrations are
represented honestly and fail locally» — «coming soon» это обещание, а не
честность.

Один компонент на все пустые вкладки, текст — данные вкладки, не копипаста.

## 5. Техдолг, зафиксированный, но НЕ берущийся в слайсе

**`gpui-component` подключён path-депом на воркетри:**

```toml
gpui-component = { path = "../Source-wt-component/gpui-component/crates/ui", ... }
```

Воркетри — временная сущность. Снесут его при чистке (а чистка воркетри у
нас уже была 2026-07-30) — сборка ChronOS встанет намертво, и причина будет
неочевидной. `docs/ARCHITECTURE.md:48` планирует переезд в `crates/ui`, но
`crates/ui` сегодня занят нашим `chronos-ui`.

Задача отдельная, инфраструктурная, трогает `Cargo.toml` воркспейса —
shared-файл, координация за архитектором. **В слайс 3 не входит**, чтобы не
смешивать переезд зависимости с рефактором панели: сломается — не поймём
что именно.

## 6. Порядок задач

```
T168 (контракт вкладки + System в модуль)  →  T169 (14 вкладок + пустые состояния)
```

Последовательно: T169 садится на контракт, который T168 отдаёт. Параллелить
нечего — это ровно та ошибка, которую мы не сделали в слайсе 1.

**Параллельно и вне слайса** (зона не пересекается с `side_panel_right/**`):

- **T170** — глобалы дока не ставятся никогда. При составлении заданий
  нашёл корень: `bar::widgets::dock::register` (`dock.rs:149`) — **мёртвая
  функция, ноль вызовов**. Виджет попадает в бар через `instantiate`
  (`bar/widgets/mod.rs:47`) в обход неё, поэтому `DockMenuState` и
  `DockConfigSignal` не устанавливаются, а `config::reload_cache()` не
  вызывается на старте. Отсюда паника из лога T166 — контекстное меню дока
  мертво **всегда**, а не при какой-то раскладке `bar.toml`; условие
  воспроизведения, которое я дал в T167, было перевёрнутым.
  Второй симптом — три из пяти пинов не рисуются — уехал в ту же задачу:
  файл и причина общие, а две задачи на один файл всё равно пришлось бы
  гнать последовательно.

**Третий раз за неделю компилятор промолчал о мёртвой `pub fn`** — T166
(`pult_display_info`) и теперь `dock::register`. `pub fn` в модуле,
экспортированном из `lib.rs`, под dead-code не попадает. Проверка «функция
реально зовётся» — грепом, а не доверием к зелёной сборке.

## 7. Проверка слайса

Общее для обеих задач слайса:

- `cargo test -p chronos`, `cargo clippy -p chronos --all-targets`,
  `cargo build --release -p chronos`
- **живой прогон обязателен**: `RUST_LOG=info`, релизный бинарь, кадры
  `grim`, переключение вкладок и режимов **по IPC**
  (`set-workspace-mode:<mode>`, `toggle-side-panel-right` в
  `$XDG_RUNTIME_DIR/chronos.sock`) — рестарты не нужны, это доказано в T167
- кадры смотреть **глазами**, при мелком тексте — вырезать и увеличить:
  `magick f.png -crop WxH+X+Y +repage -filter point -resize 300% out.png`

Слайс закрывается QA-смоком после T169. В него уходит остаток P2 слайса 2:
вкладка ушла из набора режима → фокус на System **без закрытия панели**.
В T167 это осталось непроверенным — на обоих кадрах активна была System.

## 8. Что считается провалом слайса

- Композиция по режиму сломалась (рейл Developer ≠ 14, Gamer потерял группу
  настроек) — регрессия T165.
- Вкладка пересоздаётся при каждом переключении — потеря состояния.
- Все вкладки инстанцируются на старте — плата за то, чем не пользуются.
- `view.rs` не похудел: если после T168 в нём по-прежнему ~800 строк и
  ветвление по вкладкам, контракт не сделан, а обёрнут.
