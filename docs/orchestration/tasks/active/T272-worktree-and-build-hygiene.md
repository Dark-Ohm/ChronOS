# T272 — гигиена воркетри и сборки: правило + разовая чистка

**Приоритет:** P2 — не фича, но прямо сейчас жжёт время исполнителей.
**Роль:** ARCHITECT (правило) + любой исполнитель (разовая чистка).
**Зона:** `docs/ARCHITECT.md`, каталог воркетри, `.gitignore` при
необходимости. Кода в `crates/` НЕ трогает — не конфликтует ни с T263, ни
с T266, ни с T269, ни с T271.

## Улики (всё за 2026-08-13, один день)

1. **Сборка падает не из-за кода.** У исполнителя T266 первый
   `cargo build --release -p chronos` завершился `exit 101`, повторный
   упёрся в таймаут 600 с. Правка была doc-only — код физически не
   участвовал. Главный подозреваемый — общий `target/` между основным
   деревом и воркетри при параллельных сборках.
2. **Прецедент уже оплачен.** Ровно на этом я однажды чуть не обвинил
   исполнителя в несамодостаточном коммите: общий `CARGO_TARGET_DIR`
   между деревом и воркетри ломает сборку так, что выглядит как дефект
   работы. Урок записан, но в процесс не превращён — и вот повтор.
3. **Воркетри копятся.** На утро было пять деревьев, из них два мёртвых:
   `ChronOS-wt-t267` (задача принята и слита ещё вчера) и
   `verify-0b3aed7` (проверочное дерево от 3 августа, коммит давно в
   `master`). Оба снесены сегодня вручную, оба прожили лишнее.
4. **База воркетри может не содержать зависимость.** `ChronOS-wt-t266`
   создан от `77428c6` — то есть от `master` БЕЗ коммита T263, хотя план
   T266 прямым текстом требует базу с T263 (обе задачи правят
   `theme_config.rs`). Поймано до начала кодовой работы, но случайно.

## Правило (пишется в `docs/ARCHITECT.md`, раздел дисциплины)

1. **База воркетри доказывается, а не предполагается.** Перед стартом
   работы: `git -C <worktree> log --oneline -1` и проверка, что нужные
   зависимые коммиты в базе присутствуют (`git merge-base --is-ancestor
   <dep> HEAD`). Если тикет зависит от другого — назвать коммит-базу в
   задании явно.
2. **Свой `target/` на воркетри.** Ни при каких обстоятельствах не
   делить `target/` между деревьями, которые собираются параллельно.
   Проверка перед разбором ЛЮБОГО непонятного отказа сборки: `echo
   $CARGO_TARGET_DIR` и `ls -d ../ChronOS-wt-*`.
3. **Инструмент подозревается раньше кода.** Необъяснимый `exit`,
   таймаут, «несамодостаточный коммит» — сперва проверяется окружение
   (target, воркетри, ядро/модули, allowlist), потом обвиняется работа.
4. **Воркетри умирает вместе с задачей.** Тикет принят и слит → дерево
   сносится в том же действии, что и перенос тикета в `done/`.
   Долгоживущее исключение допускается только с записанной причиной
   (пример: `ChronOS-wt-measure` — база замеров gpui-component).

## Разовая чистка (исполнителю)

1. Пройти `git worktree list`, для каждого дерева установить: чьё, под
   какую задачу, задача жива или закрыта, есть ли незакоммиченное
   (`git status --short`) и коммиты вне `master`
   (`git log --oneline master..HEAD`).
2. Мёртвые — `git worktree remove`, затем `git worktree prune`. **Сносить
   только те, где статус чист и ноль коммитов вне master.** Есть хоть
   что-то — не трогать, вынести в отчёт списком.
3. Проверить слитые ветки: `git branch --merged master`. Список — в
   отчёт, удаление ветвей БЕЗ отдельного разрешения архитектора не
   делать.
4. Замерить, сколько занимают `target/` живых деревьев (`du -sh`), и
   написать число в отчёт. Контекст: по прошлому замеру реальный жир
   экосистемы — ~185 ГБ в `target/` соседних проектов, и это
   периодически возвращается.

## Верификация

- `git worktree list` в отчёте ДО и ПОСЛЕ.
- Для каждого снесённого дерева — доказательство, что терять было нечего
  (вывод `git status --short` и `git log master..HEAD`, оба пустые).
- Правило из раздела выше присутствует в `docs/ARCHITECT.md`.
- Кода в `crates/` диф не содержит — `git diff --stat` это показывает.
