# T270 — Wayland drag-out не завершает drag-сессию: pointer-grab остаётся у композитора навсегда

**Зона: репозиторий `Source/` (форк gpui), НЕ ChronOS.**
Файл: `Source/gpui_linux/src/linux/wayland/client.rs`.
Приоритет: критический — баг убивает ввод во всём десктопе до перелогина.

## Симптом (наблюдался живьём трижды, 12–13 августа 2026)

Мышь и скролл перестают работать во ВСЁМ композиторе: ни один клиент не
получает событий указателя. При этом:

- бинды Hyprland на SUPER (drag/resize окон) продолжают работать — значит
  композитор события получает, но не доставляет никому;
- в хостовом логе мёртвой сессии libinput продолжает отдавать полные циклы
  PRESS→RELEASE (313 строк button-debounce) — железо и libinput исправны;
- `pkill chronos`, `hyprctl eval` с `follow_mouse 0/1`, убийство awww —
  не помогают;
- лечится только перелогином.

**Триггер установлен:** перетаскивание файла из Chronos-FM **наружу**, в
другое приложение. Дроп внутри самого FM симптом не даёт.

## Ложные следы (закрыты, не повторять)

- ~~popup grab в контекст-меню ChronOS~~ — ChronOS T264 часть A сняла

  без единого открытого меню. Гипотеза мертва.
- ~~hover-strip/peek правой панели ChronOS~~ — подозревался, не при чём.
- Репро `Source/gpui/examples/popup_grab_repro.rs` не воспроизводит баг ни
  в labwc, ни во вложенном Hyprland — он проверял не тот путь.

## Корневая причина (по коду, не по памяти)

Введена коммитом `5eeb892` «feat(gpui): external drag-out — Wayland
wl_data_source uri-list (T052)» от 2026-08-11 — первая смерть ввода
случилась 12-го.

`wl_data_device::start_drag` заводит **имплицитный pointer-grab на уровне
композитора** на всё время drag-сессии. Сессия считается завершённой,
когда клиент-источник получил `dnd_finished` (или `cancelled`) и уничтожил
`wl_data_source`. Наш код этого не делает:

1. `client.rs:~352` `start_external_drag()` — создаёт `data_source`,
   вызывает `offer(text/uri-list)` и `data_device.start_drag(...)`.
   **`set_actions()` не вызывается.** При `WL_DATA_DEVICE_MANAGER_VERSION
   = 3` (client.rs:569) для версии ≥3 источник обязан объявить действия;
   без этого согласование действий не проводится и `dnd_finished` не
   приходит вообще.
2. `client.rs:2591` `impl Dispatch<wl_data_source::WlDataSource>` —
   обрабатывает ровно `Send` и `Cancelled`, всё остальное `_ => {}`.
   `DndDropPerformed`, `DndFinished`, `Target`, `Action` — проглочены.
   `data_source.destroy()` стоит ТОЛЬКО в ветке `Cancelled`.

Итог: при успешном дропе наружу источник живёт вечно, drag-сессия не
закрывается, композитор держит грэб. Обрати внимание — это ровно тот
класс дефекта, который в ChronOS запрещён правилом «не глуши ошибку
`let _ =`»: здесь `_ => {}` в матче событий протокола проглотил
обязательный шаг протокола, и цена — трое суток отладки не в том репо.

## Что сделать

1. **`set_actions`** перед/при старте драга: `DndAction::Copy |
   DndAction::Move` (Copy как минимум — приёмная сторона уже использует
   `const ACTIONS: DndAction = DndAction::Copy` на client.rs:2421, держать
   согласованно).
2. **Обработать полный жизненный цикл источника** в диспатчере
   (client.rs:2591):
   - `DndFinished` → очистить `state.drag.source_paths`, вызвать
     `data_source.destroy()`;
   - `DndDropPerformed` → зафиксировать факт дропа (курсор отпущен), но
     НЕ уничтожать источник до `dnd_finished` — приёмник ещё читает данные
     через pipe, ранний destroy оборвёт передачу;
   - `Cancelled` → как сейчас (очистка + destroy), проверить, что
     `source_paths` не теряется у параллельного клипбордного источника —
     сейчас обе роли ходят через один и тот же `Dispatch<..., ()>`, и
     `Cancelled` от клипбордного источника обнулит `drag.source_paths`
     живого драга. Разделить роли по user-data типу (не `()`), либо
     проверять, что событие пришло от того же объекта.
   - `Action` / `Target` → как минимум не молчать: залогировать, чтобы
     следующий такой дефект был виден в `RUST_LOG=info`.
3. **Явно не оставлять `_ => {}`** в этом матче: перечислить оставшиеся
   варианты. Молчащая ветка здесь уже стоила десктопа.

## Статус (2026-08-13): код принят, живой прогон открыт

Код в `Source`: `18ea90a` (основная правка) + `48b2c1f` (copy-only).
Статику проверил сам по дереву `Source`:

- `set_actions()` вызывается ДО `start_drag` — как требует version 3;
- `data_source_completion()` считает завершением только `Cancelled` и
  `DndFinished`; `DndDropPerformed` → `None`, источник живёт, пока
  приёмник читает pipe (ранний `destroy()` оборвал бы передачу);
- роли типизированы (`DataSourceRole::Clipboard | Drag(paths)`), `Send`
  для драга берёт пути из роли, а не из общего `state.drag` — гонка
  «клипбордный `Cancelled` обнулил пути живого драга» устранена по
  конструкции;
- поздние события старого источника отсекаются по `ObjectId`;
  catch-all не молчит, а логирует `warn`.

**Решение по действиям драга: только `DndAction::Copy`.** Первая редакция
этого тикета требовала `Copy | Move` — ошибка автора тикета. Обработки
события `Action` нет, а по протоколу при выбранном `Move` **источник
обязан сам удалить оригинал**; Chronos-FM этого не делает. Результат был
бы тихой ложью в UX: пользователь «переместил» файл, получил копию и
целый оригинал на месте. Объявлять `Move` можно только вместе с реальным
удалением на стороне FM — до тех пор copy-only.

Осталось (закрывается только живьём, статика здесь не считается):

1. Пять прогонов drag-out из Chronos-FM наружу с `RUST_LOG=info` по
   чеклисту «Верификация» выше — мышь и скролл живы после каждого.
2. Отдельно проверить, что приёмник получает файл (`dnd_finished` без
   данных — другой дефект).
3. Убедиться, что принимающие приложения показывают именно копирование,
   а не перемещение (следствие copy-only).

Прогон отложен по решению архитектора: мышь нужна пользователю для
работы, а тест по своей природе ломает ввод при регрессе.
