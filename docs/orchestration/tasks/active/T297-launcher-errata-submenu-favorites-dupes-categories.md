## Часть A — подменю Desktop Actions не рендерится / мышь не видит

**Симптом (владелец):** контекстное подменю (дочернее) багованное, плохо
рисуется, курсор его не ловит.

**Причина (найдена).** `app_menu.rs::window_options()` (`~L400-410`)
считает высоту окна через `estimate_menu_height(&entry)` — оценку
**только** строк верхнего меню (`app_menu.rs:183`). Wayland-окно — surface
фиксированного размера под эту оценку. `menu.submenu("Desktop Actions",
...)` (`app_menu.rs:278`) — родной flyout `gpui_component::menu`,
раскрывается ВПРАВО/вниз от родительского пункта, т.е. требует места
**за пределами** окна верхнего меню. Surface этого места не имеет —
контент либо клипается по границе окна (визуальный баг), либо рисуется
за её пределами и физически не получает ввод (Wayland не доставляет
события по контенту вне буфера surface — ровно то, что уже разбирали
на pin-catcher баге, тот же класс проблемы, другая причина).

**Не чинить как T275-catcher** (там была неверная система координат
дырки, здесь — окно физически мало). Варианты:
- Растить окно/`estimate_menu_height` с учётом ширины/высоты самого
  широкого submenu, когда `!entry.actions.is_empty()` (простой путь,
  но может исказить позиционирование родительского меню относительно
  анкора).
- Не использовать родной `submenu()` для Desktop Actions — плоский
  список без вложенности (actions обычно 1-3 пункта, вложенность не
  критична), тогда лишнего места не нужно вообще. **Рекомендация** —
  этот путь проще и не трогает allocator окна.
Выбор — на исполнителе, описать в отчёте одной строкой.

## Часть B — добавление в избранное не обновляет сетку live

**Симптом (владелец):** избранное появляется только после переоткрытия
лаунчера.

**Причина (найдена).** `toggle_favorite(id: &str)` (`app_menu.rs:198`)
пишет `launcher_config::update(...)`, но **не принимает `cx`** и никогда
не зовёт `notify_config_changed(cx)` — в отличие от `toggle_pin`
(`app_menu.rs:204-219`), у которой `cx: &mut App` есть и вызов на месте.
Даже если сигнал позвать, `LauncherView`'ский вотчер конфига
(`view.rs:254`, `state::watch(cx, config_signal, |this, _, cx| {
this.apply_hidden_filter(); })`) вызывает **только** `apply_hidden_filter`
— пересборки секций Favorites/Recents/Folders там нет вообще.

**Фикс:** `toggle_favorite` берёт `cx: &mut App`, зовёт
`notify_config_changed(cx)` в конце (симметрично `toggle_pin`). Вотчер в
`view.rs:254` должен звать не только `apply_hidden_filter`, но и
пересборку секций favorites/recents/folders (метод, который уже
использует `refresh_results`/`new` для их первичной постройки — не
плодить второй путь построения секций). Live: favorite добавляется/
снимается в контекст-меню → сетка/секция обновляется без переоткрытия.

## Часть C — дубли приложений (пример: Hermes)

**Симптом (владелец):** некоторые приложения показаны дважды.

**Причина (найдена, конкретный пример).** На этой машине реально
существуют ДВА `.desktop`-файла для одного приложения:
`~/.local/share/applications/hermes.desktop` и
`/usr/share/applications/hermes-desktop.desktop`. Дедуп в `scan_all`
(`crates/services/src/applications/mod.rs:115-131`) ключуется по
`app_entry.id` (`file_stem()` — имя файла без `.desktop`), это ПО СПЕКЕ
XDG «user overrides system с тем же именем файла» — работает верно для
своего назначения, но `hermes` ≠ `hermes-desktop` как строки, так что
оба выживают как разные записи.

**Это не баг дедупа, это отсутствующая эвристика.** Настоящие лаунчеры
(GNOME Shell, KDE) сталкиваются с тем же классом дублей и обычно НЕ
решают его общей эвристикой (риск ложных склеек: два разных приложения
с похожим `Exec` — не редкость). Варианты, от дешёвого к рискованному:
1. **Не чинить в общем виде** — это artifact конкретных пакетов
   (`hermes-desktop.desktop`, вероятно, сторонний .deb/.rpm конвертер),
   не архитектурная дыра. Задокументировать как known-limitation.
2. Дедуп по паре `(Name, Exec без параметров/пути)` — вероятность ложной
   склейки двух разных бинарей с одинаковым именем `Name=` реальна, но
   низкая; описать компромисс в отчёте, если решите брать это направление.
3. Скрыть вручную через существующий `Hide from list` (T265-D, уже в
   дереве) — рабочий обход **сегодня**, без кода.

**Рекомендация архитектора:** вариант 1 (не чинить общей эвристикой) +
указать пользователю на вариант 3 как обход. Не заводить как часть этого
тикета без отдельного решения — слишком легко сломать что-то другое
двум разным приложениям с совпадающим `Name`.

## Часть D — категорий слишком много («тьма»)

**Симптом (владелец):** бар категорий забит, визуальный шум.

**Причина.** `build_categories` (`launcher/grid.rs`) берёт **все**
`entry.categories` без разбора. `.desktop`-спека freedesktop
(`Desktop Menu Specification`) различает **Main Categories** (~11 штук:
`AudioVideo`, `Development`, `Education`, `Game`, `Graphics`, `Network`,
`Office`, `Science`, `Settings`, `System`, `Utility`) и **Additional
Categories** (десятки узких: `IDE`, `TextEditor`, `Qt`, `KDE`, `GTK`,
`Building`, `Debugger`, ...) — вторые предназначены для слияния меню
дистрибутивов, не для показа пользователю напрямую. Многие `.desktop`
перечисляют 4-8 категорий, из которых 1-2 главные и остальные —
technical noise. Отсюда «тьма» на баре — это все они, не отфильтрованные.

**Фикс:** `build_categories` фильтрует по allow-list Main Categories
(список выше, литерал в коде, не конфиг — freedesktop-стандарт стабилен
годами). Приложение без ни одной Main-категории — не попадает в бар
вообще (только в «All»), не течёт под Additional как есть сейчас.
`filter_by_category` фильтрует `entry.categories.contains(cat)` — работает
без изменений, раз в баре остаются только валидные main-категории.
