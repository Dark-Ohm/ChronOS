## Подготовка

Release-сборка: `cargo build --release -p chronos`. Гонять только релизный
бинарь, `RUST_LOG=info`, лог в файл. Дебажная сборка для оконного кода не
доказательство.

**Сохрани копии пользовательских конфигов до начала и верни их в конце:**
`~/.config/chronos/{workspace.toml,scenes.toml,dock.toml,bar.toml,monitor.toml}`.
Это машина архитектора, а не стенд.

`ydotool` на этой машине: **absolute-координаты = экран / 2** (подтверждено
трижды — T157/T158/T162). Сокет `YDOTOOL_SOCKET=/run/user/1000/.ydotool_socket`.
Два вывода: DP-1 2560×1440 в (0,0), HDMI-A-1 1920×1200 в (2560,0).

## Пункты смока

Каждый — с кадром `grim` и/или строкой лога. Нумеруй файлы улик по номеру
пункта, складывай в один каталог, путь укажи в отчёте.

### P1. Композиция рейла следует режиму
Старт в Developer → правый рейл показывает все 10 вкладок. Переключить режим
(клик по виджету в баре либо `set-workspace-mode:gamer` по IPC) → рейл
показывает System + группу настроек, разработческие инструменты исчезли.
**Настроечные вкладки в Gamer остаются** (спека строка 149) — если их нет,
это дефект. Кадры обоих состояний.

### P2. Панель не закрывается при смене режима
Открыть в Developer вкладку, которой нет в Gamer, переключиться в Gamer.
Ожидание: панель **осталась открытой**, активной стала System. Если панель
схлопнулась — дефект, кадр обязателен.

### P3. Состав дока следует режиму
Developer → закреплённые из `dock.toml` (или дефолт режима, если файла нет).
Gamer → дефолты режима. Кадры дока в обоих режимах.
**Отдельно проверь известное ограничение:** в Gamer закрепить приложение →
оно запишется в `dock.toml`, но не покажется (Gamer игнорирует пользовательские
пины). Это известно и заведено как долг слайса 3+ — не дефект, но подтверди
поведение фактом, а не ссылкой на этот абзац.

### P4. Сцена переживает рестарт
Создать `~/.config/chronos/scenes.toml` руками: `version = 1`, две сцены с
разными `rail_tabs`/`dock`, `[last]` с обоими режимами. Убедиться, что
оверрайд сцены **перебивает** дефолт режима (рейл и док берут состав из сцены).
Рестарт шелла → состав тот же.
**Затем главное:** добавь в файл сцену с заведомо мусорным `mode = "гамер"` и
ключ `[scene.windows]` с парой полей. Погоняй переключения режимов,
рестартни, и **сравни файл побайтово до и после** (`sha256sum` или
`diff`). Файл обязан остаться нетронутым — ни мусорная сцена, ни
`[scene.windows]` не должны исчезнуть. Это ровно тот дефект, за который T164
не приняли с первого раза; проверка обязательна.

### P5. Весь хром на одном выводе
`hyprctl layers` + кадры обоих мониторов. Бар, обе боковые панели, обе полоски
наведения, док, десктопный терминал — на пультовом выводе, ничего не
размножено на второй. В логе — `Opening bar on pult display DisplayId(N)`.

### P6. Вотчер стартует на чистой машине
Убрать `~/.config/chronos/monitor.toml` (в копию!), стартовать шелл.
Ожидание: шелл поднялся, `bar::init` авто-назначил вывод и записал uuid в
файл, а вотчер **подхватил его в течение ~3 секунд** и работает. Покажи `cat`
файла после старта. Это второй дефект первого захода T166 — проверяем, что
он закрыт.

### P7. Уведомление о пропаже вывода — без хирургии над компоновщиком
`hyprctl keyword monitor <имя>,disable` на **Hyprland 0.56.1 с Lua-конфигом
не работает** — отвечает «keyword can't work with non-legacy parsers. Use
eval.» Проверено архитектором. **Не воюй с этим и не отключай монитор
архитектора наугад.**

Вместо этого используй то, что вотчер перечитывает конфиг каждый тик:
на живом шелле впиши в `monitor.toml` заведомо несуществующий uuid.
Ожидание в течение ~3 с: `WARN monitor: configured display ... disconnected,
shell using fallback`, **видимое уведомление** на экране (кадр!), шелл жив,
хром остался на фолбэк-выводе. Верни настоящий uuid → `INFO ... reconnected`
и второе уведомление. Кадры обоих тостов.

**Отдельно проверь, что на холодном старте ложного «reconnected» НЕТ** —
первая выборка не переход. В первом заходе T166 такой тост стрелял на каждом
запуске; исправление надо подтвердить: старт с корректным конфигом,
уведомлений о дисплее в первые 10 секунд быть не должно.

Если хочешь попробовать настоящий hotplug через `hyprctl eval` — можно, но
**только** если сначала выяснишь корректный синтаксис и убедишься, что вывод
возвращается. Свалишь сессию архитектора — это провал задачи, а не героизм.
Не уверен — не трогай, напиши «не проверено, нужен физический hotplug».

### P8. Ноль паник
Лог за весь прогон без `panicked at`. **Известное:** при некоторых раскладках
бара в логе встречается `no state of type ...DockMenuState exists` — глобал
ставится только в `bar/widgets/dock.rs:151`, то есть при баре без виджета
дока его нет. Если поймаешь — воспроизведи (какая раскладка `bar.toml`, какое
действие) и опиши отдельным пунктом. Это находка уровня отдельной задачи, не
твой дефект и не дефект слайса 2.
