# T264 — popup grab у контекст-меню убивает ввод во всём композиторе

**Приоритет:** P0 — блокирует ЛЮБОЙ живой смок ChronOS. Каждый прогон стоит
пользователю сессии Hyprland (мышь мертва до перелогина).
**Роль:** FRONTEND (ChronOS, Часть A) + FORK (Source/gpui_linux, Часть B).
**Зависимость:** блокирует T263 (`docs/orchestration/tasks/active/
T263-context-menus-anchor-and-visual-fidelity.md`) — его живая верификация
невозможна, пока это не починено.

## ОБНОВЛЕНИЕ 2026-08-12, вечер: гипотеза грэба ОПРОВЕРГНУТА

Третье воспроизведение случилось на сборке, где часть A уже применена, то есть
при `grab: false` у обоих контекст-меню, **и без единого открытого меню**.
Последнее, что шелл написал в лог за полминуты до смерти ввода:
`side_panel_right: opened (peek)` → `side_panel_right: closed`. Контекст-меню в
этом эпизоде не открывалось вообще.

Решающее наблюдение пользователя: **при зажатом SUPER мышь работает** — можно
таскать и ресайзить окна биндами Hyprland. То есть композитор нажатия получает
и свои бинды исполняет, но **не доставляет pointer-события ни одному клиенту**;
скролл мёртв по той же причине. Это застрявший pointer-focus/implicit grab на
поверхности, которой уже нет, а не проблема попапа.

Проверено в момент поломки и не помогло:
- `pkill -x chronos` — процесс мёртв, ввод не вернулся;
- `hyprctl eval 'hl.config({ input = { follow_mouse = 0 } })'` и обратно в 1 —
  оба `ok`, эффекта ноль (обычный `hyprctl keyword` в Lua-форке отвечает
  «keyword can't work with non-legacy parsers, use eval»);
- убийство `awww-daemon` — после него в `hyprctl layers` **ноль** слоёв, ни
  одной чужой поверхности, ввод всё равно мёртв.

Итог: часть A вреда не принесла и остаётся в дереве (грэб контекст-меню нам не
нужен), но **лечила не ту болезнь**. Новый главный подозреваемый —
`side_panel_right` peek/hover-strip: overlay-слой шириной 4px у правого края,
который по наведению маппит и уничтожает поверхность прямо под курсором. Это
ровно тот класс операций, что оставляет висячий pointer-focus. Второй
кандидат — общий путь уничтожения окон в форке
(`gpui_linux/src/linux/wayland/window.rs`), а не popup-специфика.

Что делать дальше по части B (переписано):
1. Повторить с отключённым hover-strip/peek правой панели и посмотреть,
   выживает ли ввод за тот же сценарий работы.
2. Инструментировать путь уничтожения поверхностей: логировать каждое
   создание/уничтожение окна с типом и id, чтобы в следующий раз лог показывал
   последнюю уничтоженную поверхность, а не молчал.
3. Клетка — второй TTY на DRM (вложенная бесполезна, см. ниже).

## Симптом (живая улика, 2026-08-12, архитектор + пользователь)

1. Запущен release-бинарь `target/release/chronos` (собран 18:06:33, свежее
   всех исходников), `RUST_LOG=info`, лог `/tmp/t263-smoke.log`. Бар поднялся
   на DP-1 как layer-shell `0 0 2560 32`, PID 8167.
2. Пользователь делает ОДИН физический правый клик по dock-иконке в баре
   (примерно `x=51, y=16`).
3. После этого клика **перестают работать обе кнопки мыши во всей системе** —
   не только в ChronOS. Курсор двигается, клики не доходят никуда.
4. `pkill -x chronos` (процесс подтверждённо мёртв, `hyprctl layers` без
   единого нашего слоя, `hyprctl clients` без наших окон) **ввод НЕ
   восстанавливает**. Лечится только рестартом Hyprland (перелогин).
5. Это второе воспроизведение. Первое — сессия миньона по T263 (см. отчёт
   `docs/orchestration/tasks/report/T263-context-menus-anchor-and-visual-
   fidelity-report.md`), там оно было списано на синтетический right-click
   через ydotool. **Это была неверная атрибуция:** сегодня ydotool не
   использовался вообще, клик был физический.

## Что уже доказано и переспрашивать не надо

- **Ядро видит клики нормально.** Чтение сырых событий с физической мыши
  (`/dev/input/event7`, Logitech G502) в момент поломки даёт чистые пары:
  `EV_KEY code=272 value=1` → `value=0` (левая), `code=273 1` → `0` (правая).
  Ни одного залипшего `value=1`. Железо, USB, kernel, ydotoold — вне
  подозрений. Скрипт-читалка: `struct.unpack("llHHi", ...)` по 24 байта из
  `/dev/input/eventN`, фильтр `type == 1`; пользователь в группе `input`,
  root не нужен.
- **В композиторе не остаётся наших surfaces.** После kill `hyprctl layers`
  показывает только `awww-daemon`, `hyprctl clients` — только kitty и
  chronos-fm.
- Вывод: состояние висит **внутри Hyprland** — сит держит pointer-grab,
  привязанный к уже уничтоженному xdg_popup. Клиент мёртв, грэб — нет.
- `hyprctl dispatch` в Lua-Hyprland 0.56.2 не работает (синтаксис ушёл в
  `hl.dsp.*`), обойти focus-переключением из CLI нельзя.

## Механика (гипотеза, проверить, не принимать на веру)

- `crates/app/src/tray_menu/mod.rs:201` и `crates/app/src/dock/
  context_menu.rs:223` открывают окно с `PopupOptions { grab: true, .. }`.
- `Source/gpui_linux/src/linux/wayland/client.rs:898-905` превращает это в
  `xdg_popup.grab(&seat, serial)`, где serial — последний
  `SerialKind::MousePress`/`KeyPress`.
- `Source/gpui_linux/src/linux/wayland/window.rs:524-528` при закрытии окна
  дёргает `xdg_popup.destroy()`.
- Подозрение: popup уничтожается, пока грэб активен, и/или в неверном порядке
  (родитель раньше потомка, либо destroy изнутри обработчика самого грэба), и
  Hyprland остаётся с dangling grab. Отдельно проверить путь T263
  «смена tray-иконки/dock-entry ⇒ старый popup закрывается и создаётся
  новый» — там уничтожение происходит из середины обработки клика.
- Контрпример, который надо объяснить: `crates/app/src/notifications/
  history_popup/mod.rs:135` тоже `grab: true` и живёт в проде без этого
  эффекта. Разница: левый клик, отсутствие пересоздания popup, отсутствие
  вложенного `gpui_component::Root`. Что именно из этого решает — часть
  задачи, а не готовый ответ.

## Часть A — P0-митигация в ChronOS (делать первой)

Цель: вернуть возможность живого смока, не дожидаясь корневой причины.

1. `tray_menu/mod.rs` и `dock/context_menu.rs`: открывать popup с
   `grab: false`.
2. Дизмисс без компоузерного грэба: клик вне карточки внутри нашей surface —
   свой `on_mouse_down` → close; потеря фокуса/`PopupDone` от компоузера —
   уже обработаны в T263-дереве, не ломать.
3. Клавиатура: `Escape` должен закрывать меню и без грэба
   (`KeyboardInteractivity::OnDemand` остаётся).
4. Unit-покрытие: закрытие по клику вне карточки и по Escape.
5. Явно зафиксировать в коде комментарием, ПОЧЕМУ grab выключен, со ссылкой
   на T264 — иначе кто-нибудь вернёт `true` через месяц.

Приёмка части A: пользователь делает правый клик по dock-иконке и по
tray-иконке, меню открывается, закрывается кликом вне и Escape, и **после
всего этого мышь продолжает работать**. Это главный критерий, а не тесты.

## Ход части B: что уже проверено архитектором (2026-08-12, не переоткрывать)

Написан минимальный репро `Source/gpui/examples/popup_grab_repro.rs`: layer-shell
«бар» + popup, четыре варианта — `L-grab`, `R-grab`, `R-destroy` (программный
`remove_window()` через 1.5 с при живом грэбе), `R-nograb`.

Результаты живых прогонов:

1. **Вложенный labwc** — все четыре варианта, ввод жив.
2. **Вложенный Hyprland** (тот же бинарь 0.56.2, минимальный Lua-конфиг
   `scratchpad/t264-nested.lua`) — все четыре варианта, ввод жив.
3. **Настоящий release-ChronOS во вложенном Hyprland** — открыто трей-меню с
   кликом по пункту (`tray_menu: clicked menu item id=38`) и dock-меню правым
   кликом по kitty-иконке (unpin-меню появилось). Ввод жив в обоих случаях.

Значит: сама связка «popup + grab + destroy» ни на wlroots, ни на Hyprland
ввод не убивает, и код T263 во вложенной сессии тоже. Гипотеза «виноват
`grab: true`» пока держится **только на корреляции по времени** — прямых
доказательств нет.

Улика из хостового лога мёртвой сессии
(`/run/user/1000/hypr/<sig>/hyprland.log`): после смерти клика libinput
продолжал отдавать полные циклы `Plugin:button-debounce ... PRESS → RELEASE →
IS_UP` (313 строк за сессию). То есть нажатия доходили до композитора, а он их
не доставлял никому. Уровень поломки — Hyprland, не железо и не libinput.

**Ограничение вложенной клетки, из-за которого она бесполезна для части B:**
вложенный Hyprland работает на Wayland-бэкенде, libinput в нём не участвует
вообще (ноль строк debounce-плагина против 313 в хосте), и выход всего один
против двух физических. Всё, что завязано на libinput-путь, DRM-сессию или
мультимонитор, эта клетка поймать не может по построению.

**Следующая клетка (делать так, а не в живой сессии):** второй TTY. Ctrl+Alt+F2,
логин, `Hyprland -c <минимальный lua>` на DRM-бэкенде, внутри — release-ChronOS,
правый клик по dock/tray. Там настоящий libinput и настоящий seat; если ввод
умрёт, он умрёт в этом сеансе, а Ctrl+Alt+F1 возвращает нетронутую основную
сессию. Только этот прогон может подтвердить или похоронить гипотезу грэба.

## Часть B — корневая причина в форке (после A)

Воспроизводить **не на ChronOS**, а на минимальном примере в `Source/`:
одно layer-shell (или обычное) окно + один `WindowKind::AnchoredPopup` с
`grab: true` + закрытие popup программно. Образцы примеров — `Source/gpui/
examples/`, см. скилл `examples-and-visual-checks`.

Проверить по порядку:
1. Умирает ли ввод, если popup закрыт по `PopupDone` от компоузера (штатный
   путь) — ожидание: нет.
2. Умирает ли, если мы уничтожаем popup сами, пока грэб активен — ожидание:
   да, это и есть баг.
3. Что меняется, если перед `xdg_popup.destroy()` сначала уничтожить все
   дочерние surfaces и/или отпустить грэб явно.
4. Является ли это багом Hyprland (тогда — минимальный wayland-репро и issue
   в hyprwm, ссылку положить в тикет) или нарушением протокола с нашей
   стороны (тогда — фикс в `window.rs`, порядок destroy).

Фикс в форке — отдельный коммит в `Source/`, с записью в `Source/PATCHES.md`
если трогается вендоренный код.

## Резолюция (2026-08-13) — причина внешняя, тикет закрыт

Виновник найден и это НЕ ChronOS: смерть ввода вызывает **drag-out файла
из Chronos-FM наружу**, в другое приложение. Механизм — незавершённая
Wayland drag-сессия в форке gpui: `wl_data_source` не получает
`set_actions()`, а `DndFinished` проглочен веткой `_ => {}` в диспатчере
(`Source/gpui_linux/src/linux/wayland/client.rs:2591`), поэтому
`destroy()` вызывается только при отмене. Композитор держит имплицитный
pointer-grab вечно. Введено коммитом `Source@5eeb892` (T052, 11 августа) —
первая смерть ввода 12-го.

Лечение — **`T270` в зоне `Source/`** (`active/T270-wayland-dnd-source-
never-finishes.md`). В ChronOS чинить нечего.

Обе гипотезы этого тикета мертвы и повторять их не надо:
- popup grab — снят в части A, симптом воспроизвёлся снова без меню;
- hover-strip/peek правой панели — не при чём.

Часть A (`grab: false` в `dock/context_menu.rs:227`, `tray_menu/mod.rs:205`
+ 4 теста) остаётся в дереве: безвредна и снижает риск, но лечила не ту
болезнь. TTY-клетка и репро `popup_grab_repro.rs` больше не нужны.

Запрет синтетических кликов по ChronOS и «один прогон = одно действие»
снимаются: живые смоки T263/T265-0 разблокированы. Единственное правило,
которое остаётся, — не таскать файлы из Chronos-FM во время сессии, пока
T270 не закрыт.
