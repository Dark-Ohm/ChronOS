## Что сделано

Реализован вариант **B** (список известных имён) по предпочтению архитектора.

### Изменения в `crates/app/src/bar/layout_config.rs`

1. **`known: BTreeSet<String>`** — новое поле в `BarLayoutConfig` с `#[serde(default)]`. Старые конфиги без поля десериализуются с пустым `known`.

2. **`migrate_new_builtins() -> bool`** — двухфазная логика:
   - **Фаза 1 (bootstrap):** `known` пуст → записать в него все имена из текущего конфига. Виджеты НЕ добавляются. Возвращает `false`.
   - **Фаза 2 (миграция):** `known` непуст → `BUILTIN_NAMES - known` = по-настоящему новые виджеты → вставить на позиции из `Default`. Обновить `known`. Возвращает `true`.

3. **`insert_at_default_pos()`** — вставляет виджет перед первым соседом из Default, который уже есть в секции. Если сосед не найден — append.

4. **`find_in_default()`** — helper, ищет имя в `Default` и возвращает `(section, index)`.

5. **`save()`** — расширен: перед записью `known` дополняется всеми именами из `left + center + right`. Пользователь, сохранивший раскладку, «видел» все текущие виджеты.

6. **`load()`** — после парсинга вызывает `migrate_new_builtins()`. Если миграция вставила виджеты (`true`) — персистит конфиг, чтобы петля не повторялась при каждом рестарте. Это единственное отступление от правила «no silent write on load» — альтернатива (миграция вставляет виджет каждый запуск) хуже.

7. **`sanitized()`** — прокидывает `known` из оригинала в отфильтрованный конфиг.

## Как работает миграция на практике

### Сценарий: пользователь с bar.toml, код добавил `workspace_mode`

1. **Первый запуск** (старый конфиг, `known` пуст):
   - `migrate_new_builtins()` → bootstrap: `known` = {dock, separator, workspaces, mpris, cava, project, volume, ...}. `workspace_mode` не в `known` и не в секциях → **не вставляется** (bootstrap возвращает `false`).
   - `save()` не вызывается (нет изменений).

2. **Пользователь сохранил через edit-mode** (или hot-reload):
   - `save()` → `known` расширяется всеми текущими именами. Но `workspace_mode` всё ещё не в конфиге → не в `known`.

3. **Второй запуск** (конфиг с `known` ≠ ∅, `workspace_mode` ∉ `known`):
   - `migrate_new_builtins()` → `BUILTIN_NAMES - known` = {`workspace_mode`} → вставка на позицию 1 в `right` → `known` обновлён → `save()` персистит.
   - Виджет появляется в баре.

4. **Третий запуск** (конфиг с `workspace_mode` ∈ `known`):
   - `migrate_new_builtins()` → `BUILTIN_NAMES - known` = ∅ → ничего не делает. `save()` не вызывается.

### Сценарий: пользователь удалил `volume` из bar.toml

1. `known` содержит `volume` (пользователь его «видел»).
2. `migrate_new_builtins()` → `volume` ∈ `known` → не вставляется.
3. После рестарта `volume` остаётся удалённым.

## Приёмка архитектора (2026-07-31): ПРИНЯТО с двумя эрратами

Отчёт заявлял DONE при зелёных тестах. Живой прогон показал, что фича **не
работала вообще**. Оба дефекта — того же класса, что подвёл T160: юнит-тесты
проверяли фазы по отдельности, а связка между ними была разорвана.

### Дефект 1 — bootstrap не персистился, фаза 2 не наступала никогда

`migrate_new_builtins()` при пустом `known` заполнял его **в памяти** и
возвращал `false`. `load()` вызывает `save()` только при `true`. Значит
`known` на диск не попадал, следующий старт снова видел пустое поле, снова
делал bootstrap — и так вечно. Фаза 2 не достигалась.

Отчёт это фактически описывает сам, в разделе «Как работает миграция»: шаг 2
требует, чтобы **пользователь сохранил раскладку через edit-mode**. То есть
починка требовала ручного действия пользователя — ровно того, ради устранения
чего задача и заводилась.

**Доказано живьём до фикса:** вернул твой оригинальный `bar.toml`, два полных
рестарта — `grep -c known` = 0, `grep -c workspace_mode` = 0. Конфиг не тронут,
виджет не приехал.

**Фикс:** bootstrap возвращает `true`. Плюс тест `migration_reaches_phase_two_
on_second_pass` — он проверяет не фазы по отдельности, а **связку**: три
прохода подряд дают bootstrap → вставку → идемпотентность.

### Дефект 2 — виджет вставал не туда

`insert_at_default_pos()` искал якорь только среди **успешников**: «вставить
перед первым соседом, который идёт после меня в `Default` и есть у
пользователя».

На твоём конфиге это дало позицию 0. В `Default` после `workspace_mode` идёт
`separator`, твой правый кластер с `separator` начинается — виджет уехал к
левому краю кластера вместо места рядом с project-пилюлей. `separator` вдобавок
повторяется в секции, так что якорем не годится вовсе: `position()` берёт
первый попавшийся.

**Фикс:** якорь на **ближайшего предшественника** (идём от ближнего к дальнему),
успешник — только запасной вариант, `separator` исключён из якорей в обе
стороны. Регрессионный тест `migration_anchors_on_predecessor_not_successor`
воспроизводит ровно твою раскладку.

### Что сделано верно и это стоит сказать

Выбор варианта B обоснован и реализован правильно. Двухфазность —
**не костыль, а единственно корректное решение**: на первом взгляде отличить
«никогда не видел» от «удалил сознательно» нечем, поэтому записываем текущий
набор и добавляем только то, что появится позже. Цена — два рестарта для
виджета, вышедшего в одном релизе с миграцией; это записано в док-комментарии,
чтобы следующий читатель не счёл багом.

Раздел «Что НЕ сделано» честный, живой прогон отдан архитектору осознанно.
