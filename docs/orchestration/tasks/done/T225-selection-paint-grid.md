# T225 — Выделение текста рисуется «синей сеткой» (D5)

**Статус:** active, не начата  
**Источник:** `docs/TBD.md` D5, live dogfood 2026-08-03 — «мышью выделение текста,
синяя сетка глючит»  
**Приоритет:** P0 edit UX  
**Зона: ФОРК**, не ChronOS — `chronos-ecosystem/Source/gpui-component`. Правила
вендоринга и `PATCHES.md` обязательны, патч должен пережить бамп апстрима.

## Корень (найден чтением, не гипотеза)

`Source/gpui-component/crates/ui/src/input/element.rs`, функция
`layout_match_range` (L518–660). Выделение строится **одним залитым полигоном**,
обведённым вокруг всех выделенных строк:

- прямой проход (L633–637) кладёт на каждую строку три точки —
  `top_right`, `bottom_right`, `bottom_left`;
- обратный проход (L639–647) кладёт только `top_left`, и **мостовую точку
  добавляет лишь при `next.top_left.x > corners.top_left.x`**;
- итог скармливается `PathBuilder::fill()` (L654–659) как один контур.

Отсюда два дефекта:

1. **Полигон самопересекается.** Когда у строк сильно разные горизонтальные
   границы (выделение начато с середины строки, короткая строка между длинными,
   мягкий перенос), обведённый контур пересекает сам себя. Заливка
   самопересекающегося контура по правилу ненулевого/чётного пересечения даёт
   ровно то, что видно: часть областей залита, часть выбита — «сетка».
2. **Мост только в одну сторону.** Обратный проход обрабатывает случай, когда
   следующая строка начинается правее, и **не обрабатывает** обратный. Там контур
   срезается по диагонали, и заливка уходит не туда.

Дополнительно `end_x = end_x.max(start.x + px(6.))` (L588) — костыль «минимум
6px для пустых строк» — навязывает шестипиксельные култышки там, где реальное
выделение на строке нулевой ширины.

**Важно:** та же `layout_match_range` обслуживает и подсветку результатов поиска
(`layout_search_matches`, вызов на L1827). Значит дефект общий для обоих, и
чинить надо один раз — но и проверять оба.

## Решение

Отказаться от идеи «один контур вокруг всего выделения». Рисовать **по одному
прямоугольнику на видимую строку** — столько путей (или квадов), сколько строк в
выделении. Так делают редакторы, и это структурно исключает самопересечение:
каждая фигура выпуклая, порядок обхода не важен, мостовые точки не нужны.

Требования:

- убрать костыль минимальной ширины: пустая строка внутри многострочного
  выделения рисуется на всю ширину строки либо на ширину пробела, осознанно и с
  комментарием — но не «6px, потому что иначе ничего не видно»;
- мягкие переносы (`wrapped_lines`, L577–609) остаются корректными: каждая
  визуальная строка — свой прямоугольник;
- поиск (`layout_search_matches`) чинится тем же кодом, а не копией.

Отдельно проверить слоистость заливки: в `paint` (L2030–2047) выделение
красится дважды — `cx.theme().selection` и `secondary_selection`. Если оба слоя
полупрозрачны и накладываются на одну область, это само по себе даёт разнотон.
ChronOS цвет выделения **не переопределяет** (`crates/app/src/theme_config.rs`
трогает только `editor_active_line*`), так что источник — стоковая тема форка.

## Приёмка

Тесты форка на построение фигур (чистая геометрия, без окна):

- однострочное выделение → один прямоугольник;
- многострочное, где первая строка начата с середины → фигуры не пересекаются;
- случай «следующая строка начинается **левее**» — тот, что сейчас без моста;
- пустая строка внутри выделения;
- строка с мягким переносом.

**Live (обязателен, «зелёные тесты для оконного кода ничто»):** в правой панели
открыть Editor на длинном файле и тянуть мышью выделение — вниз, вверх,
через пустые строки, через перенесённые. Заливка ровная, без сетки и култышек.
Затем то же для подсветки поиска. Кадры `grim` в обеих темах.

**Коммит (в форке):** `input : selection paints per-line quads, not one polygon (T225)`.
Запись в `PATCHES.md` обязательна.
