# T216 — Right panel resize: absolute (self-correcting) drag model

**Статус:** code in tree, live smoke pending  
**Источник:** live dogfood 2026-08-03 — «правую панель так же колбасит при малейшем
ресайзе» (после T214, который считался закрытым)  
**Приоритет:** P0 — ломает daily driver

## Что было не так

T210 (покадровые дельты) и T214 (anchor + `start_x += Δw` в `render`) — обе модели
**накапливающие**: ширина считалась от запомненного состояния, а не от текущей
геометрии.

Панель прибита к правому краю (`Anchor::TOP | Anchor::RIGHT`), поэтому рост ширины
двигает **левую** кромку окна влево. Координаты `DragMoveEvent` — оконно-локальные,
то есть меряются от этой самой уезжающей кромки. `window.resize()` на Wayland
асинхронна: между записью в state и реальным `configure` от компоновщика прилетают
события, померенные по **старой** геометрии. Накапливающая модель обязана держать
свою бухгалтерию в такт с ack'ами — она не может, и каждое рассинхронизированное
событие засчитывает смещение дважды.

**Замер (старый бинарь, живой drag влево):** ширина шла
`895 → 806 → 792 → 773 → 684 → 524 → 382 → … → 40 … → 960` — разгон в оба упора.

### Ложный след (для протокола)

Первый диагноз — «drag-события не доходят до обработчиков» — был **неверен** и
опирался на отсутствие в логе строк `resize drag started/move`. Этих строк там и не
могло быть: они добавлялись той же правкой, а бинарь был старый. Доказательство
обратного лежало в тех же логах: `window.resize` во время drag'а меняла ширину
десятки раз произвольными дробными значениями, а их пишет только `update_resize`.

## Фикс

**Абсолютная самокорректирующаяся модель** (`resize_target_width` в `mod.rs`):

```
pointer_screen = window_left + current_x,  window_left = screen_right - actual_w
держим схваченную точку под курсором  =>  desired_left = pointer_screen - grab
desired_w = screen_right - desired_left  =  actual_w - current_x + grab
```

`actual_w` берётся из `window.bounds()` — из той поверхности, относительно которой
померен `current_x`, а **не** из нашего state (он убегает вперёд между ack'ами).
Накопления нет: отставший кадр повторяет ту же цель вместо того, чтобы её удваивать.
Побочно это ровно то поведение, которое просил пользователь — **кромка приклеена к
мыши**, а не догоняет её.

Из `render` убрана компенсация `resize_start_x += Δw` — при абсолютной модели она
считала бы то же смещение кромки второй раз.

## Раскрытие rail → content остаётся на mouse-down (важно)

Попытка убрать авто-раскрытие (казавшееся косметикой) **сломала drag полностью**:
rail-only окно шириной 40px, первое движение уводит курсор за пределы поверхности
раньше, чем GPUI успевает начать drag-сессию. Замер: `resize drag started` есть,
`resize drag move` — ноль. Раскрытие даёт жесту достаточно широкое окно, чтобы он
родился. Грехом T214 было не раскрытие, а накопление после него.

При раскрытии grab-offset переписывается в новый кадр: `grab = press_x + (target - w)`,
иначе первое же событие прочитает курсор как «глубоко в body» и схлопнет панель назад.
