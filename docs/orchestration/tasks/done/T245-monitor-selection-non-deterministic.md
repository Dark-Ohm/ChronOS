# T245 — шелл непредсказуемо переезжает на HDMI-A-1 вместо DP-1

**Приоритет:** P0 (пользователь поднял как топ-1, "это бесит" — важнее
визуальных находок T223-аудита).
**Роль:** FRONTEND (Rust, GPUI) + живая диагностика на этой машине.
**Источник:** `docs/orchestration/tasks/report-log/T223-design-audit-report-v4-reshoot.md`
§4 "Системные проблемы", пункт 2; наблюдалось дважды за одну ночь
(2026-08-04→05) без действий пользователя.

## Контекст — механизм должен быть детерминирован, но не является

Выбор "пультового" (chrome) монитора живёт в `crates/app/src/monitor.rs`
(читать файл целиком — он маленький и хорошо задокументирован в шапке).
Цепочка резолва (`pult_display()`, строки 131–187):

1. `~/.config/chronos/monitor.toml` → `chrome_monitor = "<uuid>"` — если
   `uuid` совпал с одним из живых `cx.displays()`, используем его.
2. Иначе — fallback: `largest_display_index()` (строки 80–93) — просто
   максимальная площадь среди `cx.displays()`.
3. Первый успешный резолв **дозаписывает** `monitor.toml` (auto-designate,
   строки 174–184) — это единственная задокументированная причина, по
   которой шелл вообще может "переехать": если сохранённый uuid перестал
   матчиться живому дисплею.

**На этой машине сейчас** (`cat ~/.config/chronos/monitor.toml`):
```
chrome_monitor = "56f01978-2d1e-5e26-bbe4-cc5fd992f8af"
```
`hyprctl monitors`: DP-1 = Samsung LC32G5xT, 2560×1440 (площадь
3,686,400 — больше), HDMI-A-1 = Dell U2412M, 1920×1200 (площадь
2,304,000 — меньше). Раз в последнюю загрузку шелл сел на HDMI-A-1, а не
на DP-1 (площадь меньше DP-1, так что largest-by-area фолбэк это НЕ
объясняет) — значит либо (а) сохранённый uuid `56f01978-...` сейчас
матчится HDMI-A-1, а не DP-1 (uuid "уехал" между дисплеями), либо (б)
`d.uuid()` у форка GPUI не стабилен между запусками/hotplug-циклами для
одного и того же физического монитора.

## Что нужно сделать

1. **Живая диагностика первым делом, не гадать по коду.** Добавить
   (временно или постоянно — решить по находке) `tracing::info!` в
   `pult_display()` печатающий для КАЖДОГО дисплея из `cx.displays()`:
   `d.id()`, `d.uuid()`, bounds, и что зарезолвилось. Прогнать
   `chronos-stop && chronos-start` несколько раз подряд (5+), смотреть
   `journalctl --user` (или туда, куда льётся stderr — см. `RUST_LOG`
   рецепт в skills/chronos-shell/SKILL.md, раздел "live automation from
   sandbox", коммит `17bde3c`) — какой uuid репортится для DP-1/HDMI-A-1
   на каждом запуске, меняется ли он.
2. **Если uuid у GPUI-форка нестабилен** (наиболее вероятная гипотеза —
   `d.uuid()` может быть построен из session-order/connector-index, а не
   из EDID/hardware-serial) — это баг/ограничение форка
   `Source/gpui`, искать `fn uuid` в платформенном Wayland-бэкенде
   (`Source/gpui/src/platform/linux/wayland/...` или аналог), сверяться
   со skill `chronos-gpui` (что фактически форк умеет отдавать по
   дисплею — EDID? connector name?). Если стабильного EDID-serial нет —
   рассмотреть **connector name** (`DP-1`/`HDMI-A-1` — эти у Hyprland
   стабильны между рестартами compositor'а, пока физическая топология не
   меняется) как альтернативный или дополнительный ключ вместо/вместе с
   uuid в `monitor.toml`.
3. **Если uuid стабилен, а проблема в другом** (например, `cx.displays()`
   в момент вызова `bar::init` ещё не успел перечислить DP-1 — гонка
   перечисления на Wayland, уже упомянутая в комментарии `bar/mod.rs:662`
   "Small delay to allow Wayland to enumerate displays") — увеличить
   задержку или сделать резолв монитора ре-триггерящимся при позднем
   hotplug-событии, не только при старте.
4. Зафиксировать причину в коде (комментарий в `monitor.rs`) и в
   `docs/DECISIONS.log`, если решение нетривиальное (например, смена
   ключа uuid→connector name — это архитектурное решение, не мелкий
   фикс).

## Резолюция (2026-08-05) — корень найден, закрыт

**Корень — НЕ uuid, а auto-designate-крысиный капкан.** `d.uuid()` форка
стабилен: `UUIDv5(NAMESPACE_DNS, wl_output.name)` — чистая функция имени
коннектора (`DP-1`/`HDMI-A-1`). Проверено: uuid конфига `56f01978-…` =
`uuid5(NS_DNS, "HDMI-A-1")`, канонический из шапки `monitor.rs`
`09e7b298-…` = `uuid5(NS_DNS, "DP-1")`. Конфиг был **переписан** с DP-1
на HDMI (mtime 02:52:34, ночь инцидента): при временном отсутствии DP-1
(DPMS-сон / поздний `wl_output Done`) фолбэк выбирал HDMI-A-1, и старый
код навсегда записывал его uuid в `monitor.toml`.

**Фикс:** `should_auto_designate` — запись конфига только на true first
run; существующий uuid авторитативен и не перезаписывается. Добавлены
постоянные `info!`-резолв-лог и `debug!`-по-дисплеям. Конфиг возвращён
на `09e7b298-…` (DP-1).

**Верификация:** 5/5 живых рестартов — бар на DP-1, резолв
`via configured-uuid`, конфиг не тронут; анти-капкан с мусорным uuid —
WARN+fallback без перезаписи; `cargo test --release -p chronos --lib --
monitor` 12/12; release-сборка чистая.
