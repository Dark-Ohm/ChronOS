## Корень: мы не объявляем клиентских возможностей

`transport.rs:124`:

```rust
cx.send_request(InitializeRequest::new(ProtocolVersion::V1))
```

`InitializeRequest` (agent-client-protocol-schema, `agent.rs:52-71`)
несёт поле `client_capabilities: ClientCapabilities` — мы оставляем его
дефолтным, то есть говорим агенту «я не умею ничего». Для сравнения,
Zed (`crates/agent_servers/src/acp.rs:756-780`, локальный чекаут
`/home/neo/Projects/zed-main`) объявляет:

```rust
acp::ClientCapabilities::new()
    .fs(acp::FileSystemCapabilities::new()
        .read_text_file(true)
        .write_text_file(true))
    .terminal(true)
    .auth(acp::AuthCapabilities::new().terminal(true))
    .session(ClientSessionCapabilities::new().config_options(...))
    .elicitation(...)
```

Агент по этим флагам выбирает ветку поведения. Пустые капабилити —
причина, по которой мы получаем от Hermes обеднённый поток и пустые
селекторы. Поэтому **порядок работ развёрнут**: сначала хендшейк
(D0), потом повторный смоук, и только потом добивание остатка. Часть
симптомов ниже может отвалиться сама — это нормально и это надо
зафиксировать в отчёте, а не «починить» задним числом.

## Дефекты

### D1 — тул-карточка `write:` навсегда в `pending`, args/result пусты

**Улика (лог 2026-07-27 04:54Z, релизный бинарь, RUST_LOG=info):**

```
04:54:41  ACP raw: ToolCall       tool_id=tc-f0f092e570ac  title=write: /home/neo/created.txt     status=Pending  raw_input=false
          ← tc-f0f092e570ac в логе больше не встречается НИ РАЗУ
04:55:01  ACP raw: ToolCall       tool_id=tc-ab59cba38f8a  title=terminal: rm /home/neo/created.txt  status=Pending  raw_input=false
04:55:02  ACP raw: ToolCallUpdate tool_id=tc-ab59cba38f8a  status=Some(Completed)  raw_output=false  content=1
```

Файл при этом реально создан. Вывод: **Hermes не закрывает
`write_file`-туд**, а ChronOS честно рисует присланное. Плюс
`raw_input=false` у обоих тулов — Hermes не шлёт аргументы вообще;
Result у `terminal` берётся из `content`.

**Что на стороне Hermes** (исходники —
`/home/neo/.hermes/hermes-agent/`, Python, чужой репо):
`build_tool_complete` вызывается не по завершении тула, а из
`step_callback` на СЛЕДУЮЩЕМ шаге агента, разбором `prev_tools` по
очереди на имя тула (`acp_adapter/events.py:244`). У `write_file` в
дополнение к общему пути висят `capture_local_edit_snapshot` и
`build_edit_proposal` (`events.py:157-177`) — у `terminal` их нет, и
это единственная содержательная разница между закрывшимся и
незакрывшимся тулом. Похоже на проглоченное исключение в этой ветке.
Проверить это можно будет только после D4 (стдерр Hermes).

**Твоя часть — не врать пользователю:**
- Мерж идёт по `name` (`composer.rs:749`:
  `.find(|t| t.name == name)`), `id` не используется вовсе. Два тула с
  одинаковым заголовком схлопнутся в один. Чинить: мержить по `id`
  (добавить поле в `chat_view::ToolCallPreview`), `name` — только для
  отображения.
- По завершении turn'а тулы, оставшиеся в `pending`, помечать честным
  терминальным статусом (`unknown`/`stale`), а не оставлять вечный
  «pending». Образец из Zed: `mark_pending_entries_as_canceled`
  (`acp_thread.rs:3906`) — там `Pending | WaitingForConfirmation |
  InProgress` → `Canceled`. Zed делает это **только** при отмене и
  ошибке turn'а, не при нормальном завершении; нам нужен и нормальный
  случай тоже, иначе повторится ровно эта картинка.
- `tool_card.rs` — рендер проверен, корректен. Не трогать без причины.

**Приёмка:** живой прогон с созданием файла → карточка не остаётся
`pending` после конца turn'а; если Hermes прислал результат — он
виден. Скриншот `grim` + кусок лога с `ACP raw:`.

### D2 — turn может зависнуть навсегда, без таймаута и без Cancel

**Наблюдение:** turn 2026-07-26T23:44:41Z. Стриминг шёл до 23:44:46,
потом тишина: ни `ACP streaming reply complete`, ни `ACP send failed`,
ни `connection terminated`. Процесс Hermes жив. Панель висела на
«Thinking…» бесконечно; выход только через «+» с потерей контекста.

**Требуется:**
- Таймаут на turn: ~120 c с момента ПОСЛЕДНЕГО полученного события, не
  с начала turn'а (длинные легитимные turn'ы с тулами рвать нельзя).
- По таймауту: пометить сообщение агента ошибкой, снять «Thinking…»,
  вернуть статус `Connected`, отменить таски, закрыть висящие тулы
  (см. D1).
- Видимая кнопка **Cancel/Stop** на время активного turn'а. Zed:
  `AcpThread::cancel` (`acp_thread.rs:3891`) — флашит стрим, гасит
  элиситации, помечает висяки, шлёт `connection.cancel`. У нас
  минимум: локальная отмена + `session/cancel` агенту.
- Логи на границах turn'а: старт, конец с причиной (ok / timeout /
  error / cancel).

### D3 — `transport` обрабатывает команды строго последовательно

`transport.rs:138-141` — `while let Some(cmd) = cmd_rx.recv().await {
execute_command(cmd, &cx, &mut active_session).await }`. Один

разделяемым `active_session` (сейчас это `&mut` в цикле — нужна
нормальная синхронизация, не `unwrap()` на мьютексе). Это был п.5

### D4 — stderr Hermes не читается в реальном времени

`AcpAgent::from_args` отдаёт stderr агента библиотеке ACP; мы видим
его только посмертно, в поле `data` при `connection terminated`. Пока
процесс жив, но повис, мы слепы — и именно поэтому D1 нельзя добить с
нашей стороны.

**Требуется:** читать stderr процесса и лить построчно в `tracing`
под таргетом `hermes.stderr` (debug; warn на строках с
ERROR/Traceback). Если библиотека не отдаёт пайп — описать в отчёте,
что именно мешает, и предложить альтернативу. Не выдумывать обходной
путь молча.

**Это приоритет №2 после D0:** без него дальнейшая диагностика Hermes
идёт вслепую.

На всех живых кадрах селектор показывает плейсхолдер «Model»,

## D6 — уточнение от архитектора (2026-07-27, после чтения твоих правок)

Твой комментарий в `client.rs:318-327` утверждает, что `stopReason`
«is returned from `send_prompt` / `ProxySessionMessages` and consumed
there, so `SessionMessage::StopReason` never lands in `update_rx`».
**Это неверно.** Смотри `agent-client-protocol-0.11.1/src/session.rs:560-572`:

```rust
pub fn send_prompt(&mut self, prompt: impl ToString) -> Result<(), Error> {
    let update_tx = self.update_tx.clone();
    self.connection.send_request_to(Agent, PromptRequest::new(…))
        .on_receiving_result(async move |result| {
            let PromptResponse { stop_reason, .. } = result?;
            update_tx.unbounded_send(SessionMessage::StopReason(stop_reason))?;
```

Библиотека сама кладёт `StopReason` ровно в тот канал, из которого
читает `read_update()`. Механизм есть — он не срабатывает.

Проверено архитектором, чтобы ты не тратил на это время:
- `PromptResponse` (schema 0.12.0, `agent.rs:3068-3098`) **не** имеет
  `deny_unknown_fields`; `usage` под `DefaultOnError`; `stop_reason`
  обязателен и в ответе Hermes присутствует и валиден
  (`{"stopReason":"end_turn","usage":{…}}`). Версия «падает
  десериализация `PromptResponse`» маловероятна, но проверяется
  логом в колбэке.

**Что от тебя требуется:** инструментировать путь доставки и показать
логом, где именно теряется `StopReason` — не долетает ли ответ до
`on_receiving_result`, падает ли `result?`, или `unbounded_send`
уходит в закрытый канал. Отдельно проверь свою же правку D3: команды
теперь идут через `tokio::spawn`, а `ActiveSession` живёт под
`Arc<Mutex>` — не рвётся ли регистрация обработчика ответа, когда
хэндл сессии перемещается между тасками.

**Про твой обходной путь** (`TURN_COMPLETE_TIMEOUT`, закрытие turn'а по
тишине, `client.rs:200-214`): как страховка — принимается и остаётся.
Как единственное лечение D6 — **нет**. С ним каждый нормальный ответ
будет висеть лишние секунды перед тем, как панель признает его
законченным, и пользователь получит «подтормаживающий» чат вместо
мгновенного. Страховка должна срабатывать только когда штатный путь
не отработал, и в лог при этом обязана падать строка, что сработала
именно страховка.

## ЗАХОД 6 — ЛАЙВЛОК ЗАКРЫТ: coop-бюджет tokio (2026-07-27, 19:15, архитектор)

Корень найден и подтверждён замером, а не рассуждением. **Это не UI-баг.**

Зонд в форке (`runnable.metadata().location` каждые 5000 задач) показал
417 935 000 runnable'ов от двух задач: `composer.rs:744` (стриминговый цикл)
и `composer.rs:651` (ACP-таск). Стек поймал форму: `Runnable::run` →
`RawTask::schedule` (raw.rs:438) внутри собственного `poll` → `Ping::ping`.
Задача будит саму себя во время своего же опроса.

Механизм. `main.rs:52` крутил весь GPUI внутри `rt.block_on(...)`. tokio
выдаёт coop-бюджет **на каждый poll внешнего future** (`runtime/park.rs:284`),
`Budget::initial()` = 128 (`task/coop/mod.rs:115`). Но `app.run()` из первого
же poll не возвращается никогда — цикл calloop живёт внутри него. Значит один
бюджет на 128 операций на всё время жизни процесса, без восполнения. Каждый
`rx.recv()` / `time::timeout` / `Mutex::lock().await` на главном потоке тратит
единицу; после исчерпания `poll_proceed` отдаёт Pending **и будит себя**
(`task/coop/mod.rs:372-407`). Форк усиливает это до 100% CPU:
`dispatcher.rs:276-281` на непустом проходе re-ping'ует себя и не сбрасывает
readiness.

**«Ровно 125» = 128 минус пара операций старта сессии.** Ни длина ответа, ни
время, ни высота контента здесь ни при чём — гипотеза про переполнение
видимой области тоже мимо.

Проверка предсказанием (не постфактум): временный зонд
`tokio::task::coop::has_budget_remaining()` в цикле composer'а. Предсказано:
перевернётся в `false` около 125 и панель встанет ровно там. Получено:
`event #124 remaining=true`, `event #125 remaining=false`, панель встала.

Фикс — `44ba823`, `crates/app/src/main.rs`: `let _rt_guard = rt.enter();`
вместо `rt.block_on(async { app.run(..) })`. `enter()` даёт `Handle::current()`
и `tokio::spawn`, но не накладывает coop-бюджет на поток; многопоточный
рантайм крутят его собственные воркеры.

| | до | после |
|---|---|---|
| события за ход | 125, зависание | 975, `turn END (reason=ok)`, 10374 симв. |
| coop-бюджет | `false` на #125 | `true` на всех 975 |
