## 1. Что говорит спека

§14 пункт 4: «Developer hybrid-workbench minimum: **Files, Terminal,
Build/Logs, Preview, System**».

System сделана в слайсе 3 и живёт в `tab/system.rs`. Остаются четыре.

§4.1 про то, чем ChronOS обязан быть, а чем нет:

> read-oriented project tree with later file operations behind explicit
> capability work
> embedded PTY/VT terminal
> lightweight editor for configuration, scripts, logs, snippets, and quick fixes
> build, test, task and run orchestration
> logs and diagnostics
> browser or GPUI preview surface

И жёсткая граница, которую нельзя размывать:

> ChronOS must not claim editor, debug, or document integration that the
> external application cannot provide.

## 2. Главное решение слайса: код у нас уже есть

Проверено архитектором 2026-07-31, а не предположено.

### 2.1 Files — берём из Chronos-FM **слой FS**, но не UI

**Уточнено разведкой T175 — первая редакция этого раздела была неточной.**
Я написал «берём из Chronos-FM, не пишем заново». Верно наполовину.

`../Chronos-FM` — проект того же автора на том же GPUI-форке
(`github.com/Dark-Ohm/Chronos-GPUI`), и **разъезд форков ничтожен**:
Chronos-FM на `ee80b72`, ChronOS на `99cab5e`, два коммита в одну сторону.

**Что переносится почти как есть — ~400–450 строк:**

- `chronos-fm-services/src/fs/listing.rs` (195) — `ListParams`,
  `ListResult`, `list_dir_sync`. **Ноль GPUI**, чистый `std::fs`.
- `chronos-fm-models::FileEntryDto` (45) — голые данные + `serde`.
- сортировка из `explorer/entries.rs` (~80).
- тонкий `Error`/`Result` (~20) — или заменить на свой.

`fs/ops.rs` (389) — копирование, перемещение, корзина. Кладём **как
библиотеку без проводки в UI**: §4.1 прямо говорит «later file operations
behind explicit capability work». Тогда и зависимость `trash` не нужна.

**Что НЕ переносится — и это главный вывод разведки:**

`explorer/` — не 3566 строк, как я посчитал, а **5244** с поддеревом
`view/`. И это UI отдельного приложения:

| препятствие | где |
|---|---|
| `ExplorerPage` — это `Page` trait + split + session KV, не одиночная сущность | `page.rs:648-649`, `:32-39` |
| `PaneItem`/`PaneGroup` — чужой page-framework | `pane_group.rs:28` |
| своя тема `chronos_fm_ui::theme`, не наш `chronos_ui::Theme` | `view.rs:5` |
| `reload()` зовёт `list_dir_sync` **синхронно на UI-потоке** | `navigation.rs:17-25`, `view.rs:62` |
| layout: sidebar 180 + listing + preview ≥240 | `view.rs:104-132` |
| ширина таблицы: 400+120+120+180+60+48 = **~928 px** | `config.rs:34-49` |

**Наша вкладка Files объявлена 440 px.** Таблица FM в 2.1 раза шире. Втащить
её можно, только раздув панель до 700+, а это полэкрана рабочего стола под
список файлов — плохая сделка. **440 остаётся**, UI пишем свой и узкий:
одна колонка (иконка + имя, размер приглушённым), строка пути сверху,
Enter/двойной клик — переход. Без sidebar, без бокового превью.

**Цена, посчитанная разведкой:** полный перенос UI ≈ 3–4 тыс. строк борьбы с
чужим layout и зависимостями; свой `FilesTab` поверх портированного
`list_dir_sync` ≈ 0.7–1.0 тыс. строк. Разница решает.

**Поправка по зависимостям:** я закладывал `Table` + `VirtualList` из
`gpui-component`. Проверено — `DataTable` в Chronos-FM **не используется
вообще**, нужен только `VirtualList` (`view/listing/list.rs`). По замерам
T157 это +15 KB вместо +214 KB. `Input` не нужен до фильтра и редактора.

**Кровное при переносе:** `list_dir_sync` блокирующий, а в FM его зовут
прямо в обработчике. У нас правило Runtime split (`docs/DECISIONS.log`) —
листинг обязан уходить в `cx.background_spawn` с применением результата на
foreground. Каталог по умолчанию режется лимитом 1000 (`config.rs:65`),
но и тысяча записей на UI-потоке — это заметный кадр.

### 2.2 Terminal — берём своё, оно уже в дереве

`crates/app/src/desktop_terminal/` — **724 строки**, живой PTY на
`portable_pty` (`NativePtySystem`, `MasterPty`, `PtySession`). Сегодня это
отдельная фоновая поверхность на рабочем столе; вкладке Terminal нужен тот
же движок в другом контейнере.

Вопрос, который слайс обязан решить явно: **desktop_terminal остаётся, или
вкладка его заменяет?** Моя позиция — остаётся: это разные сценарии
(фоновый терминал на обоях против терминала в панели). Но тогда PTY-движок
надо вынести из `desktop_terminal/view.rs` в общее место, а не копировать.

### 2.3 Build/Logs и Preview — вот это новое

Под них готового кода нет. И именно здесь легче всего нарушить §4.1: сделать
вид, что мы интегрируемся с тем, с чем не интегрируемся.

## 3. Границы слайса

**В слайсе:**

1. Вкладка **Files** — read-oriented дерево проекта. Операции с файлами
   (удаление, переименование, копирование) — **за отдельной задачей**, §4.1
   прямо говорит «later file operations behind explicit capability work».
2. Вкладка **Terminal** — PTY в панели, движок общий с `desktop_terminal`.
3. Вкладка **Build/Logs** — запуск задач и просмотр вывода.
4. Вкладка **Preview** — поверхность предпросмотра.

**Вне слайса — осознанно:**

- Полноценный редактор (вкладка Editor). §4.1 хочет «lightweight editor», но
  это отдельная работа с текстовым вводом, и у нас уже есть измеренная цена
  `gpui-component` Input (+1.84 MiB, T157). Отдельный слайс.
- Файловые операции в Files — по §4.1 за отдельной capability-задачей.
- Inspector и SourceControl — они в рейле с T169 и остаются честными
  пустыми состояниями.
- Gamer-инструменты — слайс 5.

## 4. Порядок и волны

Слайс большой, поэтому волнами. Первая — то, под что есть код.

```
волна 1:  T175 (RECON: что переносится из Chronos-FM)
              ↓
          T176 (Files)        T177 (Terminal)     ← параллельно, зоны разные
              ↓
волна 2:  Build/Logs, Preview  ← брифы пишу после волны 1
```

**Почему разведка отдельной задачей, а не сразу код.** `explorer/` — 5244
строки, написанных под отдельное приложение с роутингом и страницами. Нам
нужна одна вкладка. Без карты «это берём, это режем, это переписываем»
исполнитель либо перетащит лишнее, либо начнёт писать заново. Разведку я
сам делать не буду: это чтение чужого дерева на несколько тысяч строк, ровно
работа роли RECON.

Брифы волны 2 пишутся **после** приёмки волны 1 — иначе повторится история
T166 и T169, где я составлял зону по неполным фактам и задача выходила
невыполнимой.

## 5. Что слайс обязан не сломать

Проверено живьём в слайсе 3, регрессии недопустимы:

- рейл Developer 14 иконок, Gamer 7;
- ширина следует активной вкладке (System 400, Editor/Terminal 560);
- вьюхи вкладок создаются лениво и кэшируются;
- панель не закрывается при смене режима.

Отдельно: **Terminal объявлен как 560 px** в `preferred_content_width`. Когда
в нём появится реальный PTY, ширину надо перемерить под 80 колонок
моноширинного шрифта, а не оставлять на глаз.

## 6. Известные риски

1. **`gpui-component` подключён path-депом на воркетри**
   `../Source-wt-component/`. Files потянет `VirtualList` (`Table` не нужен —
   проверено разведкой), то есть зависимость станет критичной, а она стоит
   на временном пути.
   **Это надо чинить до волны 1**, иначе снесут воркетри при чистке — и
   сборка встанет с неочевидной причиной. Заведено как техдолг в слайсе 3,
   пора брать.
2. **Стоимость бинаря.** T157 измерил: `Input` +1.84 MiB, `Table` +199 KB,
   `VirtualList` +15 KB. Разведка уточнила: Files потянет **только
   `VirtualList`** (+15 KB), `Table` не нужен вовсе. `Input` придёт с
   фильтром и редактором — отдельный разговор.
3. **Честность §13.** Build/Logs и Preview проще всего сделать «красиво и
   неправдиво». Если интеграции нет — пустое состояние обязано говорить, чего
   именно нет, а не рисовать заглушку под рабочий инструмент.

## 7. Проверка слайса

Общее для всех задач:

- `cargo test -p chronos`, `cargo clippy -p chronos --all-targets`,
  `cargo build --release -p chronos`;
- **живой прогон обязателен**: релиз, `RUST_LOG=info`, кадры `grim`,
  переключение по IPC (`toggle-side-panel-right`,
  `set-workspace-mode:<mode>`) — рестарты не нужны;
- кадры **открывать глазами**, мелкое вырезать и увеличивать;
- лог грепать целиком на `panicked at`.

Слайс закрывается QA-смоком после волны 2.

## 8. Что считается провалом

- Слой FS переписан с нуля при живом `list_dir_sync` в Chronos-FM.
- Или наоборот: притащен UI-shell проводника (`Page`, `PaneGroup`, sidebar,
  боковое превью) в панель шириной 440.
- Перетащено больше, чем нужно вкладке (страницы, роутинг, S3, git-панель).
- PTY скопирован в два места вместо выноса в общее.
- Вкладка обещает интеграцию, которой нет.
- Регрессия любого пункта §5.
